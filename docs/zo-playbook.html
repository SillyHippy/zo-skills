1. The 60-Minute Response Limit & UI Sync Bugs
Stability
The Problem: Zo's web chat UI uses an active websocket connection. When a task takes longer than an hour, the browser connection drops or the UI stays stuck on "running" even though the script on the VPS finished 30 minutes ago.
Exact Sequential Execution Pattern:
  1. Stop running long coding or scraping commands directly in the live chat reply box.
  2. Tell Zo to write the task into a standalone script.
  3. Tell Zo to launch that script detached in the background using nohup.
  4. Tell Zo to pipe the live output into a log file at /tmp/task_run.log.
  5. Tell Zo to print the background process ID (PID) and exit immediately.
  6. Whenever you want an update, ask Zo to read the last 30 lines of that log file.
Copy prompt to launch background job: 
Do not run this task in the live foreground chat session. 

Follow these exact steps:
1. Launch the command in the background using nohup:
   nohup [YOUR_COMMAND_HERE] > /tmp/task_run.log 2>&1 &
2. Print the process ID (PID) so I know it started.
3. Exit immediately and give me a one-sentence confirmation that it is running in the background. Do not wait for it to finish.
Copy prompt to check progress: 
Read the last 30 lines of /tmp/task_run.log and check if the process is still running with `ps aux | grep [YOUR_COMMAND_NAME]`. Give me a short bulleted status update.
2. Nightly Reboots Killing MCP Servers (Grok / ChatGPT OAuth)
Persistent MCP
The Problem: Zo reboots or cycles leases overnight. If your MCP server was started in a temporary terminal tab, it dies. Grok and ChatGPT lose their OAuth connection because in-memory tokens vanish and dynamic port URLs change.
The 3 Rules for Immortal MCP Servers:
  1. Rule 1 (Disk-Backed Tokens): The MCP server MUST save tokens to a SQLite DB or JSON file (e.g. /home/workspace/.mcp/tokens.json), never in RAM variables.
  2. Rule 2 (Supervisor Autostart): Put the MCP server into Zo's user supervisor (/etc/zo/supervisord-user.conf) with autostart=true so it boots on reboot.
  3. Rule 3 (Fixed Public URL): Route traffic through a Cloudflare Tunnel connected to your own domain so Grok/ChatGPT always connect to the exact same HTTPS URL.
Copy prompt to register MCP server in Supervisor: 
I need my MCP server to automatically restart whenever this Zo Computer reboots.

Follow these exact steps:
1. Open /etc/zo/supervisord-user.conf.
2. Add a new program block for my MCP server:
   [program:my-mcp-server]
   command=[COMMAND_TO_START_SERVER]
   directory=[PATH_TO_SERVER_FOLDER]
   autostart=true
   autorestart=true
   redirect_stderr=true
   stdout_logfile=/tmp/mcp_server.log
3. Run `supervisorctl -c /etc/zo/supervisord-user.conf update` to load and start it.
4. Run `supervisorctl -c /etc/zo/supervisord-user.conf status` and show me that it is RUNNING.
3. Subagent Swarms ("Can't Fan-Out / Fan-In")
Agent Swarms
The Problem: People think Zo can't do multi-agent swarms because there is no "Subagent" button in the UI.
How It Actually Works (The 4 Steps):
  1. Zo has 32GB of RAM and full Python asyncio installed.
  2. Instead of waiting on single-turn chat steps, Zo writes an async script that fires 50 to 100+ parallel queries simultaneously.
  3. The script collects all 100 responses into a single JSON file in seconds.
  4. Zo reads that JSON file and synthesizes the final report in one turn.
Copy prompt to run parallel swarm: 
I want to run an agent swarm of 50 parallel queries to analyze [TOPIC/DATA].

Follow these exact steps:
1. Write a Python script `/tmp/run_swarm.py` using `asyncio` and `httpx`.
2. Generate 50 distinct task queries based on [TOPIC].
3. Fan out all 50 queries concurrently using `asyncio.gather()`.
4. Capture every response and error, and dump the entire list into `/tmp/swarm_data.json`.
5. Run the script.
6. Once `/tmp/swarm_data.json` is generated, read it and give me a synthesized summary of the findings.
4. Docker Alternative & Client-Dedicated Sandboxes
Security & Multi-Tenancy
The Problem: Zo runs in gVisor on Modal. gVisor blocks root mount namespaces (CLONE_NEWNS), so dockerd cannot start containers. How do you isolate a client's apps and agents without Docker?
The One-Way Linux Sandbox Architecture:
  1. Lock down /root permissions to 700 so only the admin can enter.
  2. Create a dedicated Linux user (e.g. client1) with their own home folder (/home/client1).
  3. Use Linux cgroups v1 to hard-cap their CPU to 2 cores and RAM to 3GB.
  4. Run their apps and agents under that user. They cannot touch your root workspace, but you (as root) have full access to inspect and repair their environment anytime.
Copy prompt to create client sandbox: 
Please set up an isolated, resource-throttled Linux client sandbox for `client1` on this machine.

Follow these exact steps:
1. Lock root so non-root users cannot see admin files:
   chmod 700 /root
2. Create the client user and dedicated directories:
   useradd -m -s /bin/bash client1
   chmod 750 /home/client1
   mkdir -p /home/client1/apps /home/client1/data
   chown -R client1:client1 /home/client1
3. Set up cgroups v1 resource throttling to cap client1 to 2 CPU cores and 3 GB RAM:
   mkdir -p /sys/fs/cgroup/memory/client1
   echo 3221225472 > /sys/fs/cgroup/memory/client1/memory.limit_in_bytes
   mkdir -p /sys/fs/cgroup/cpu/client1
   echo 100000 > /sys/fs/cgroup/cpu/client1/cpu.cfs_period_us
   echo 200000 > /sys/fs/cgroup/cpu/client1/cpu.cfs_quota_us
4. Create a launcher script `/usr/local/bin/run-client1.sh` that assigns the shell PID to the cgroups and runs commands via `su - client1 -c "$*"`.
5. Test that client1 gets "Permission denied" when trying to list `/root`.
5. Codex CLI & Bubblewrap (bwrap) Crashes
CLI Sandboxing
The Problem: When running OpenAI Codex or Claude Code CLI, commands crash with bwrap: Failed to make / slave: Operation not permitted.
Why this happens: Codex wraps every tool call inside Bubblewrap for safety. Because Zo is already running inside Modal's gVisor container, nested sandboxing is forbidden. Tell Codex to run directly on the host shell.
How to execute commands without Bubblewrap: 
# Codex CLI (current flags — there is no --no-sandbox):
codex --dangerously-bypass-approvals-and-sandbox -p "Your coding prompt here"
# or:  codex -s danger-full-access -p "Your coding prompt here"

# Claude Code CLI:
claude --dangerously-skip-permissions
6. Shutting Off Zo's Native Memory (Supermemory)
Context Hygiene
The Problem: Zo has two layers of memory: active conversation context and background-injected Supermemory. Zo does not provide an "Off" switch in the UI, causing stale bug fixes or old conversations to pollute new chats.
How to Completely Override It:
  1. LLMs prioritize explicit system/persona instructions over background injected context.
  2. Put an explicit instruction at the top of your Persona or System Prompt telling it to ignore native memory.
  3. Instruct it to keep state only in local files (like MEMORY.md or local SQLite).
  4. Alternative: If you route through an LLM proxy like OmniRoute, inject this system prompt at the proxy layer so it applies across all chats automatically.
Paste this into your Zo Persona / System Instructions: 
## Memory Directives
- Completely ignore all implicit, native, or background-injected cross-session memory (Supermemory).
- Do not assume prior context, past project state, or implicit preferences unless explicitly provided in the current prompt or found in local workspace files.
- Treat every new session as a clean, isolated state.
- All persistent memory and project state MUST be read from and written directly to local files in the workspace (e.g., `MEMORY.md` or a local SQLite database).
7. High Disk Writes Triggering Mid-Response Reboots
I/O Performance
The Problem: Modal automatically snapshots the persistent disk (/root and /home/workspace). When you run giant npm install runs, compile wheels, or extract multi-gigabyte zips, the disk churn locks up the snapshot engine and reboots your sandbox mid-turn.
The Golden Rule: On Zo, /tmp is the same persistent 9p disk as / — it is not RAM. The real RAM disk is /dev/shm (tmpfs). Put caches and scratch builds there so they do not churn the snapshot layer.
Copy prompt before heavy builds: 
Before building or installing anything, redirect caches and scratch to the RAM disk (/dev/shm), not /tmp:
export TMPDIR=/dev/shm
export PIP_CACHE_DIR=/dev/shm/pip-cache
export npm_config_cache=/dev/shm/npm-cache
mkdir -p /dev/shm/build

Do all cloning, compiling, or extracting in `/dev/shm/build` first.
Once finished, copy ONLY the final compiled artifact or binary to `/home/workspace`.
8. Cloudflare Limits, Custom Tunnels & Allowing AI Crawlers (is-agentic.com)
Edge Networking & SEO
The Problem: Zo's native hosting routes traffic through Zo's enterprise Cloudflare account, where "Block AI Scrapers and Crawlers" and Bot Fight Mode are locked ON. Audits like is-agentic.com get 403 Forbidden errors. Cloudflare's own Free/Pro limits still apply on a tunnel you own: 100 MB request body (413) and a default ~125s origin read timeout (524).
The 3-Step Setup (Costs Nothing):
  1. Create a free Cloudflare account at dash.cloudflare.com and add your domain.
  2. Create an API Token with full Zone/DNS/Tunnel permissions.
  3. Give Zo the API token and the prompt below. Zo will automatically install cloudflared, configure the tunnel, map the DNS, and supervisorize it.
Copy prompt to set up Cloudflare Tunnel: 
I want to make my backend running on port [PORT] publicly accessible on my domain [SUBDOMAIN.YOURDOMAIN.COM] using a Cloudflare Tunnel so we completely bypass Zo's Cloudflare proxy and allow AI agent crawlers (is-agentic.com compliance).

Here is my Cloudflare API Token: [PASTE_YOUR_CF_API_TOKEN_HERE]

Follow these exact steps:
1. Install `cloudflared` on this machine if not present.
2. Authenticate using the token and create a named tunnel (e.g. `zo-tunnel`).
3. Route DNS for `[SUBDOMAIN.YOURDOMAIN.COM]` to this tunnel.
4. Forward ingress traffic to `http://localhost:[PORT]`.
5. Add `cloudflared` to /etc/zo/supervisord-user.conf so it automatically restarts on reboots.
6. Verify the tunnel is active and test that the URL returns 200 OK.
How to Configure Cloudflare WAF to Maximize AI Agent Crawling & SEO:
  1. Turn Off AI Bot Blocking: In Cloudflare, go to Security → Bots and toggle "Block AI Scrapers and Crawlers" to Off.
  2. Disable Bot Fight Mode: Turn off Bot Fight Mode (or set Security Level to Essentially Off) so headless AI scanners don't get challenged by Turnstile.
  3. Disable Browser Integrity Check (BIC): In Security → Settings, turn BIC off so CLI agents and curl-like scrapers aren't flagged.
  4. Create a WAF Skip Rule: Go to Security → WAF → Custom Rules → Create Rule: 
    (http.user_agent contains "is-agentic") or
(http.user_agent contains "GPTBot") or
(http.user_agent contains "ClaudeBot") or
(http.user_agent contains "PerplexityBot") or
(http.request.uri.path in {"/robots.txt" "/llms.txt" "/llms-full.txt"})
    Set Action to: Skip → All remaining custom rules, WAF Managed Rules, and Super Bot Fight Mode.
💡 Static Sites: If your website doesn't have a backend and is completely static (HTML/JS/CSS), don't even use a tunnel. Deploy it directly to Cloudflare Pages. It's 100% free, has unlimited bandwidth, and has zero bot-blocking by default.
9. Zo Browser Limitations & Localhost Access
Browser Automation
The Problem: Zo Browser runs in a separate remote sandbox that cannot connect to localhost, idle times out after 5 minutes, and cannot handle 2FA/CAPTCHA challenges.
The Solution:
  1. For testing local apps: Run Playwright or Scrapling directly inside the Zo terminal. Because it runs on the Linux host, it has direct access to http://localhost:[PORT].
  2. For complex scraping & CAPTCHA takeover: Connect your script via CDP (Chrome DevTools Protocol) to external browser services like Steel.dev or Browserbase for persistent profiles and live human takeover.
Copy prompt for localhost app testing: 
Write a python script using Playwright to visit `http://localhost:[PORT]` locally on this machine, take a screenshot of the homepage, save it to `/tmp/app_test.png`, and check if there are any console errors. Run the script and show me the output.
Also verified on a live Zo box
Don't trust nproc
nproc lies under gVisor. It often prints 1 even when you paid for 4 vCPUs. RAM reporting is honest (free -h showed 32 GiB). Count CPUs from /proc/cpuinfo instead of nproc.
Copy prompt to check real CPU/RAM: 
Do not trust nproc. Print all of these and stop:
1. nproc
2. grep -c '^processor' /proc/cpuinfo
3. free -h
4. findmnt -T /tmp
5. df -hT /dev/shm
